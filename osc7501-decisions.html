D003: a list or a table keyed by task ID?

You selected Option A on October 27. Both options expose the same task records. The Rust store stays in TerminalState. This choice concerns the snapshot that Lua receives, not the protocol or record ownership. The alpha implements pane:get_program_status() as the sorted list.

Option A: a list of records

local records = {
  { id = "", state = "working" },
  { id = "build/test", state = "blocked" },
}

for _, record in ipairs(records) do
  print(record.id, record.state)
end

A list is convenient when you want to draw or inspect every task. We can return entries sorted by ID, giving repeatable output. Each entry carries its own identity and is easy to pass to formatting helpers.

The drawback is lookup: finding build/test means scanning the entries or building a lookup table. Numeric positions can change between snapshots. A root record is optional, so records[1] must not be assumed to mean the root.

Option B: a table keyed by task ID

local records = {
  [""] = { state = "working" },
  ["build/test"] = { state = "blocked" },
}

local test = records["build/test"]
if test then
  print(test.state)
end

This is convenient when a config cares about one particular task. The key is its identity, and a missing task naturally reads as nil. Comparing snapshots by ID is also straightforward.

The drawback is display order. Ordinary pairs traversal has no specified order, so stable presentation requires collecting and sorting keys. The root uses records[""], and IDs with slashes need bracket indexing. Lua iteration reference.

Recommendation: Option A for the first version, because the immediate job is producing tab indicators from the available tasks. A small Lua helper can provide ID lookup later. Option B is a reasonable choice if direct task lookup is the main interface you want to present.

Decision still open. The record set is bounded, so usability is the main consideration. Neither choice determines which state gets priority in a tab; that is a separate presentation decision.

What upstream Ghostty actually implements

At revision 291fd050b9e9, libghostty-vt validates reports and delivers them to its host. The Ghostty app's stream handler still ignores the action. The upstream change merged on 6 October 2026. Mitchell's implementation PR.

This refines the ownership recommendation below. Keep the parser stateless; put durable records in WezTerm's per-pane Rust model. Lua should read snapshots and react to changes.

What the specification already decides

Reports replace records per pane. IDs support a hierarchy. clear removes a subtree. Prompt start and attached-process exit remove working and blocked; done and error survive. Full reset clears all records. Parsing, capability replies, text validation, and limits also have defined rules. Protocol specification, revision 0.4.

We should test those rules directly. Most of our freedom lies in architecture and presentation.

The implementation choices

These are recommendations for a first native implementation. Each choice affects either reliability, configuration, or the amount of work.

DecisionAlternativesRecommended starting point
Protocol integrationNative Rust support or an OSC 1337 compatibility bridgeNative parsing in wezterm-escape-parser. A bridge is useful for a demo but changes what applications must emit.
State ownershipGUI memory, Lua globals, or terminal stateKeep typed records with the terminal. Let the mux distribute snapshots and changes to clients.
Lua interfaceRaw text, reserved user variables, or structured recordsA proposed pane:get_program_status() plus a change event. Include a revision so clients can ignore stale updates.
Scope of first releaseLocal panes only or complete mux supportPrototype locally, then include remote panes and reconnect snapshots before calling the feature complete.
Tab displayOne priority status or separate activity and attention indicatorsShow activity and attention separately. A blocked child should remain visible while another task works.
Completion acknowledgementFocus, keyboard input, or explicit dismissal; shared or per clientStart with explicit dismissal per GUI client. Keep the application record intact; hide only the completed indicator in that client.
NotificationsEvery update, selected transitions, or opt-in Lua behaviorOpt-in notifications for background panes. Deduplicate and rate-limit alerts; do not replay them on reconnect.
CompatibilityMap old progress reports into this model or keep them independentDefer the optional OSC 9;4 mapping. Test SSH and tmux passthrough separately.
Defaults and deliveryExperimental flag or default support; upstream PR or maintained forkUse a flag during development. Aim for upstream Rust support and a small Lua example, with parsing enabled by default once verified.
