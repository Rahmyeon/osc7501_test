Test the alpha, one behavior at a time

First run the automated checks. Then check what a person actually sees. You do not need Rust to do this: send a report, inspect the records, and compare the tab with the expected result.

Allow roughly 30 minutes for a first manual pass. Stop and record a failure before moving on, so we can reproduce it.

2. Check the record behavior

Run each block inside the alpha shell. Each test starts by clearing records. Look at both the tab and a fresh debug snapshot. The empty ID "" means the root task.

A. Progress updates without an extra keypress

Send-Status 'state=clear'
Send-Status 'state=working:app=cargo:progress=10'
Start-Sleep -Seconds 3
Send-Status 'state=working:app=cargo:progress=80'

Pass: the tab changes from WORKING 10% to WORKING 80% without clicking or typing again. The snapshot has one record, with ID "", app cargo and progress 80.

A static percentage is intentional. This alpha does not draw a spinner. Requiring another keypress to update would suggest a refresh bug.

B. A blocked child does not replace its parent

Send-Status 'state=clear'
Send-Status 'state=working:app=cargo:progress=25'
Send-Status 'state=blocked:id=build/tests:kind=permission'

Pass: the snapshot contains two records, root first and build/tests second. The child has effective_app cargo. The tab shows BLOCKED:permission and 2 records.

The missing intermediate build record is allowed. The child inherits its app from the nearest existing ancestor, here the root. Blocked wins over working in our example Lua formatter.

C. Reports replace the whole record

Send-Status 'state=clear'
Send-Status ("state=blocked:id=build/tests:kind=permission:title=" + (Encode-Text 'Database tests'))

Inspect now. Expect kind=permission and title=Database tests. Then run:

Send-Status 'state=done:id=build/tests'

Pass: the same ID now has state done. Its old kind and title are absent. The tab shows DONE and uses build/tests as its label.

This is replacement, not a patch that preserves omitted fields.

D. Clear a subtree without clearing a similar name

Send-Status 'state=clear'
Send-Status 'state=done:id=build'
Send-Status 'state=done:id=build/tests'
Send-Status 'state=done:id=builder'
Send-Status 'state=clear:id=build'

Pass: only builder remains. Both build and build/tests are gone.

Repeat the last command. Nothing should change or crash. Then run Send-Status 'state=clear'; the snapshot should be empty.

E. An invalid report leaves valid records alone

Send-Status 'state=clear'
Send-Status 'state=working:app=cargo:progress=42'
Send-Status 'state=error:id=bad//id'

Pass: there is still exactly one root record, working at 42%. There is no error record and no accidental change to the root.

Sending the valid working report again should keep the same snapshot contents. Manual observation cannot prove that redundant internal notifications were suppressed; source tests cover that.

F. A prompt removes temporary work but retains results

Send-Status 'state=clear'
Send-Status 'state=working:id=compile'
Send-Status 'state=blocked:id=approval:kind=auth'
Send-Status 'state=done:id=tests'
Send-Status 'state=error:id=deploy'

Inspect first: expect four records. Then send the actual shell integration marker:

$e = [char]27
[Console]::Write("$e]133;A$e\")

Pass: only deploy/error and tests/done remain, in that ID order. The tab shows ERROR and 2 records.

Merely printing an ordinary prompt does not trigger cleanup. The shell must send OSC 133 A. The alpha shell uses NoProfile, so this test sends the marker explicitly.

You have OpenCode 1.19.4 installed. It can run inside the alpha. There are two separate things to test: whether its terminal interface works normally, and whether it sends OSC 7501 reports that populate the task records.

Watch a turn from start to finish

  1. Before a prompt, press Ctrl+Shift+U and save the latest records snapshot. Esc returns to OpenCode.
  2. Ask: Explain what a Rust enum is in a few paragraphs. Do not modify any files. Watch the tab while the response streams. Inspect the records during generation if it lasts long enough.
  3. When the response finishes, inspect again. Check that typing, scrolling, rendering and resizing still work.
  4. For an approval test, use OpenCode's own permission settings to require approval for a harmless action in the playground, such as creating a small hello.txt file. When it asks, inspect the records before answering. Do not assume the action will prompt under your current settings.
  5. Answer the approval, watch work resume, then inspect after completion. Exit OpenCode through its normal quit command and inspect once more from the shell.

When OpenCode finishes at idle

Your first manual pass found that OpenCode appears to return to idle after finishing. Inspect the fresh snapshot: if that same task record says idle, the formatter should display idle. If it says done but the tab says idle, first check the other records and pane identity, then investigate presentation. We have not captured the emitted sequence, so the app-side explanation remains a hypothesis.

Keeping done visible makes an unread result easier to find. However, the terminal should apply incoming reports rather than invent completion from idle. This is worth documenting even if it does not block the alpha.

For example, inside an alpha shell in a project that already has an npm test script, run this block. It requires npm and that project's normal test setup; it does not install dependencies.

Send-Status 'state=clear'
Send-Status 'state=working:id=coursework/tests:app=npm'
npm.cmd test
$testExit = $LASTEXITCODE
if ($testExit -eq 0) {
    Send-Status 'state=done:id=coursework/tests:app=npm'
} else {
    Send-Status 'state=error:id=coursework/tests:app=npm'
}

The wrapper treats zero as success and any nonzero exit code as failure. It does not inspect individual tests, report percentages or detect permission prompts. A PowerShell launch error needs its own handling in a reusable adapter; this example assumes npm.cmd starts successfully. This simple example is separate from the native agent integrations above.

What counts as ready for your presentation?

  • You can launch a visible window and repeat the guided demo.
  • The smoke test passes, and you have checked the manual cases you plan to demonstrate.
  • You can explain that the parser recognizes reports, TerminalState owns records, and Lua chooses the tab summary.
  • You describe remote mux synchronization as deferred. Closing and reopening a local process is not a persistence test: this alpha does not save task records to disk.

Capability replies, malformed framing, size limits, eviction and redundant notification suppression have source tests. Do not treat this manual checklist as exhaustive protocol conformance or proof of performance. Remote mux, SSH combinations and other operating systems are outside this alpha's verified scope.

Check your testing judgment

These questions are optional. They help connect the observations to the architecture.

The snapshot says blocked, but the tab still says working. Where would you investigate first?

Explanation

The current snapshot already contains blocked. Investigate the tab's selection policy and the path that requests a refresh before changing parsing.

The new report omits title and the old title disappears. Is that a failure?

Explanation

A report replaces the record with that ID. Omitted optional fields disappear. This keeps an old permission reason from surviving after a task changes state.

All twelve smoke checks pass. Have we proven the tab is readable at a narrow width?

Explanation

The smoke checks compare data. Text can be correct and still overlap or truncate badly. Manual visual checks test that separate property.
