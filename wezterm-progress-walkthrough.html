One progress report, five small jobs

WezTerm already moves structured progress from a running program to a tab. OSC 7501 can extend that pattern. The additional work is tracking several tasks and keeping their states correct.

For a college project, build it as a sequence of working milestones. Reading a large repository feels different once you can name the handful of components your feature touches.

Follow a 42% report

The program writes ESC ] 9 ; 4 ; 1 ; 42 ST. 9;4 selects the progress protocol, 1 selects a percentage, and 42 is the value. ESC and ST stand for control bytes. ConEmu's protocol documentation.

Read every step without JavaScript
  1. The program writes the escape sequence.
  2. The parser produces ConEmuProgress(SetPercentage(42)).
  3. The terminal stores Percentage(42) and emits Alert::Progress because the value changed.
  4. The mux distributes the alert. A connected remote client updates its cached value.
  5. Lua sees { Percentage = 42 }. The default tab title can display a progress glyph. Sending 42 again produces no second progress alert in the terminal handler.
Try the report in your own WezTerm pane

This PowerShell command sends 42%. The second clears progress. Whether you see a symbol depends on your WezTerm build and tab configuration.

[Console]::Write(('{0}]9;4;1;42{0}\' -f [char]27))
[Console]::Write(('{0}]9;4;0{0}\' -f [char]27))

[char]27 supplies ESC. The format operator inserts it in both places; the final backslash completes ST.

Alert is an internal change message in this path. It does not mean “show a desktop popup.”

Read the implementation in order: parser, stored enum, state update, local alert forwarding, remote cache, Lua getter, default title.

Three details that prevent wrong assumptions

The parser recognizes paused state, but the terminal maps it to None. A percentage of 100 stays a percentage; this protocol supplies no distinct “done” state. Also, the progress documentation still says display requires Lua, while the current default renderer uses progress directly.

Two Rust enums appear in this path. The parser's SetPercentage(42) describes a command. The model's Percentage(42) describes the resulting stored fact.

What OSC 7501 adds

OSC 9;4 gives each pane one progress value. OSC 7501 adds named task records and richer state. We can follow WezTerm's existing architecture while changing what it stores.

ChoiceSuggested starting designReason
One record or a table?A bounded map from task ID to an owned Rust record.A running parent and blocked child both need to remain available.
Parser rules or model rules?Validate reports in the parser. Apply replacement, clearing, inheritance, and lifetime rules in the model.The parser knows the bytes; the model knows existing records and terminal events.
Changes or snapshots?Use change messages during a session and a complete snapshot when a client attaches.A new client needs current state even when the application stays quiet.
Repeated reports?Update internal recency for valid reports; suppress unnecessary display notifications when visible content is unchanged.Record eviction order and UI refreshes have different purposes.
Whole tab or active pane?Expose all pane records to Lua. Begin with a simple title example; decide built-in aggregation after that works.The existing active-pane policy can hide a different split that needs input.
Merge old progress into new status?Keep the two stores independent initially.Optional compatibility mapping creates ordering questions and can erase richer information.
Notifications and dismissal?Start with visible tab status. Add configurable notifications and client acknowledgement in a later UI step.This keeps the first complete implementation focused.

The OSC 7501 specification fixes the record rules and limits. The recommendations in this table are our architecture choices, not an existing WezTerm API.

Mux messages are serialized. WezTerm has a codec version check, so changes to its wire types need deliberate version handling. This is one reason to treat remote support as its own milestone. Codec version.

A student-sized way to approach it

This is a substantial project, especially if Rust is new to you. My earlier estimate assumed someone comfortable with terminal code. Plan several weeks of learning and implementation, with a working result at each stage.

  1. Understand and build the baseline.Get a development checkout running. Send an existing OSC 9;4 report and read its Lua value. Finish this before changing the protocol.
  2. Write and test the new parser.Start with a valid report and a query, then malformed input, size limits, and fragmented writes. The existing conemu parser test is a useful starting point.
  3. Build the record model.Test replacement, nested clearing, inheritance, eviction, prompt cleanup, process exit, and reset. A root-only experiment is useful while learning; the complete model is the release target.
  4. Make it visible locally.Add the pane getter and change delivery. Write a small Lua tab formatter. A manually emitted report should now produce a visible result.
  5. Finish remote delivery and documentation.Handle initial snapshots, subsequent changes, and codec compatibility. Add a demo, document the Lua interface, and prepare a focused pull request.

A credible project result includes tested behavior, clear design notes, and a reproducible demo. Those give you concrete material to discuss in an interview.
