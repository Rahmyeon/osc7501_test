Designing OSC 7501 in WezTerm

The useful question is which component should own each job, and what evidence supports that choice. WezTerm's code and Wez's commit explanations give us a way to answer it.

What we can learn from the repository

Imagine a program reporting that a build is running while one child task needs permission. Someone must validate the report, retain both tasks, decide what a tab shows, and refresh that tab when the facts change. Those jobs need different information.

Read the evidence labels

Stated means a comment, document or verified Wez-authored commit gives the reason. Observed means the code does it. Inferred means we explain a benefit or recommend a design. We will label our judgment rather than present it as Wez's opinion.

Many contributors work on WezTerm. A current implementation tells us about the project; a verified author and commit explanation let us attribute a particular decision to Wez. Neither guarantees that a future proposal will be accepted.

A feature crosses several small boundaries

An escape sequence arrives as bytes. Each component turns it into something the next component can use. A Rust crate is a separately compiled library or program. WezTerm's repository contains many of them.

  1. vtparse + escape parserRecognize the sequence and produce a typed command. A parser can retain incomplete input without owning persistent terminal task records.
  2. term / TerminalStateApply the command and retain terminal facts. This core has no GUI and does not directly manage a PTY.
  3. mux::Pane / LocalPaneExpose those facts through a shared pane interface. The local implementation wraps the terminal, process and PTY.
  4. Mux notificationsAnnounce changes to subscribers. Remote panes also need server, codec and client handling.
  5. lua-api-crates/muxGive Lua scripts access to pane capabilities through the shared interface.
  6. wezterm-guiPrepare title information, run formatting callbacks and render the result.

These are cooperating layers rather than one strict call sequence. The GUI builds PaneInformation directly from the pane interface; a live Lua pane method is a separate access path. Notifications tell consumers when to refresh.

Stated boundaries. The parser documents encoding and decoding without terminal emulation. The terminal crate documents a GUI-independent model with a caller-supplied writer. Read the contracts.

For OSC 7501, parsing a task ID belongs near the bytes. Clearing all descendants of that ID needs the record store. Choosing a tab color needs presentation policy. Moving all three into one place would make that component know too much.

How to decide where code belongs

Let required knowledge determine ownership

Stated. The title getter explains that TerminalState processes escape sequences without knowing about other tabs. It retains the terminal titles; the GUI handles the wider window presentation. Title design comment.

Our application. Your D002 choice, storing task records in TerminalState, follows that pattern. Record replacement, clearing and inheritance stay with the owner. Lua or the GUI can summarize those records for a tab.

A process-exit event comes from the process wrapper. It must reach the record owner. Choosing a good owner does not remove the need to connect outside events.

Use a typed command at the handoff

An enum is a Rust type with named alternatives. Existing progress uses one enum for incoming instructions and another for stored state. This small distinction makes the boundary explicit.

// Existing types, shortened. This is not OSC 7501 code.
// wezterm-escape-parser/src/osc.rs
pub enum Progress {
    SetPercentage(u8),
    Paused,
    // other commands omitted
}

// term/src/terminal.rs
pub enum Progress {
    Percentage(u8),
    None,
    // other stored states omitted
}

SetPercentage(42) tells the terminal to do something. Percentage(42) describes the result. A u8 is an unsigned 8-bit number. The types share a name but live in different modules. Source and performer.

Useful exception. The parser recognizes Paused, but the performer maps it to None. Recognizing syntax does not prove semantic support. Our capability reply must describe behavior we have actually connected and tested.

Use the common pane interface

A trait describes operations that different implementations provide. Pane lets consumers read a local pane or a remote client pane through the same interface. The Lua object resolves a pane by ID; it does not own the terminal.

Stated history. Wez merged separate GUI and mux pane Lua objects because there was no GUI-specific functionality in the GUI object. Read his explanation.

Our application. A record getter should use the existing pane API. A title-formatting snapshot is a separate connection. Existing progress supplies both a live pane:get_progress() method and PaneInformation.progress.

An empty default getter can keep another pane implementation compiling. It does not make that implementation support OSC 7501.

A stored fact and a change message solve different problems

Observed. Progress lives in the terminal. When its value changes, the performer stores the new value and sends an alert. The local pane can read the current value later. Here, Alert is an internal message; it does not automatically mean a desktop popup.

Stated history. Wez's first progress commit reused existing alerts and explicitly acknowledged that a reconnecting client would see no progress until another update, because separate state transfer was missing. Original commit.

Reconnecting does not replay a missed event in this model. Reading a snapshot recovers the current fact even if the program stays quiet. Sending the same percentage twice produces one change, matching the terminal progress handler's equality check.

Our application. Keep one task store. Decide what a change notification carries. For future remote support, implement initial state transfer as well as ongoing changes. A local-only milestone does not settle either the remote snapshot design or wire compatibility.

Do not copy a pattern as an absolute rule

Progress suppresses an identical update, while the current SetUserVar handler notifies after each assignment. For task records, a valid repeated report can refresh eviction recency without changing displayed content. These are separate concerns. Comparison feature.

Keep the input path and the GUI responsive

Stated. The PTY reader has a dedicated thread because nonblocking PTY reads are not portable across all supported platforms. The scheduler abstraction exists because GUI processing can require the main thread. Local pane alerts use that scheduler. Current comments and forwarding path.

Stated history. Wez described a large-paste blockage: a reader waits on a full channel, the program cannot finish output, and then it cannot accept more input. He removed that hard-blocking channel after rate control provided another way to manage load. Windows portability shaped the choice. Historical explanation.

Our application. Do bounded local work while processing a report. Use the established writer and notification route. Copy record data under the terminal lock, then release the lock before Lua conversion or callbacks. Check that a notification cannot synchronously reenter the same locked terminal.

format-tab-title is synchronous and must return quickly. Reading a prepared snapshot fits that contract. Waiting for a process, network response or unrelated lock would stall the GUI. Callback contract.

A bounded record store that evicts an old entry has different behavior from a channel that blocks a PTY reader. The historical deadlock does not argue against our record limit.

Keep the API small and useful

Stated history. Wez initially exposed progress to Lua, then added a default tab display in the next change. The later spinner explicitly respects custom title formatting. That supports separating state access from presentation policy. It does not imply that built-in defaults are unwelcome. Display history.

Our API should expose records with stable IDs. A chosen glyph or tab summary loses detail a different Lua formatter might need. You selected the sorted list on October 27. Both shapes below have precedent elsewhere in the repository; the comparison records the tradeoff behind your choice.

Finding one task: the same information, two access methods

Suppose the script already knows the task ID it wants: build/tests. A keyed table uses that ID as the address of its record. A list uses numbered positions, so the script searches the entries for a matching ID. The list contains the necessary information; looking through it takes extra work.

These are ordinary Lua teaching examples, not an implemented WezTerm API or a settled field contract. Both describe the same three tasks.

local records_by_id = {
  ["build"]       = { state = "working" },
  ["build/tests"] = { state = "blocked" },
  ["docs"]        = { state = "done" },
}

-- Use the known ID directly as the key.
local task = records_by_id["build/tests"]
if task and task.state == "blocked" then
  print("Tests need attention")
end

The key "build/tests" selects its associated record. The slash needs no special handling inside this quoted string. If that key is absent, Lua returns nil, meaning no value. The task and check avoids reading a field from a missing record.

local records = {
  { id = "build",       state = "working" },
  { id = "build/tests", state = "blocked" },
  { id = "docs",        state = "done" },
}

local task = nil
for _, candidate in ipairs(records) do
  if candidate.id == "build/tests" then
    task = candidate
    break
  end
end

if task and task.state == "blocked" then
  print("Tests need attention")
end

ipairs visits numbered entries in sequence. The underscore discards the numeric position; candidate holds each record. The loop checks its ID and stops at a match. If none matches, task stays nil. Both examples print the same message.

Although the target is currently at position 2, records[2] is not a reliable way to identify it. Adding or removing another task can shift positions. Sorting makes display order predictable; an ID gives a task its identity.

Self-check: what happens if a new ID sorts before build/tests?

Its numeric position can change in the sorted list, so a search must keep comparing IDs. Direct keyed access remains records_by_id["build/tests"]. This is why a list position must not become a saved task identity.

For displaying every task in order, the sorted list removes sorting work from the formatter. For finding one known task, the keyed table removes search code from the script. A helper could hide the list search, but it would still need an implementation. This Lua choice does not determine the internal Rust store's container.

D003 is accepted: a list sorted by ID. See the worked Lua examples for the alternatives considered.

Stated history. For window configuration overrides, Wez accepted data without Lua closures or userdata because those objects belong to a particular Lua context. He started with whole top-level replacements rather than a complex deep-update API. Ownership explains the restriction.

Our inference. Prefer an owned snapshot with clear field semantics over mutable handles into the record store. Decide absent values, inherited app information and field names before presenting the API as stable.

Compatibility depends on the boundary

Wez preserved old boolean font configuration when introducing a richer slant enum. The mux protocol instead checks an explicit codec version. A shared Alert enum is serialized, so adding a variant needs a wire-compatibility audit even while remote feature support is deferred. Configuration precedent · Codec contract.

Write code that fits the surrounding crate

Preserve supported configurations

Stated. Wez made the parser work with no_std and allocation, accepting slower linear lookups in some cases. The current HEAD adds checks to prevent silent regressions. no_std means the standard library is unavailable; it does not mean allocation is forbidden. Commit explanations.

Our parser should not require Lua, GUI code or an unconditional standard-library dependency. Test it separately so the full application's features do not hide a mistake.

Spend complexity on a demonstrated need

Observed and stated. Adjacent printable actions are merged to reduce heap use. Tests check action sizes. These are specific costs in frequent terminal traffic. Action representation.

Our inference. Keep task data bounded and match nearby types and ownership conventions. Use the simplest adequate store before adding caching or a generic task framework. The parser uses Rust 2024 while the terminal crate uses Rust 2018, so even neighboring crates have different constraints.

Take validation rules from the protocol

Observed. Existing OSC parsers handle invalid input differently. Some decoding is strict; optional fields can be ignored; old progress numbers are forgiving. The top-level OSC parser can preserve failed input as an unspecified command. Examples in the parser.

Our application. Implement OSC 7501's own rejection and ignore rules. Finish validation before changing a record. Do not borrow permissive behavior merely because another OSC handler uses it.

Connect lifecycle behavior and test the actual path

Stated history. A recent reset fix explains that a program could leave keyboard modes behind after an unclean exit, and RIS did not clear them. Initialization had not been enough; recovery needed its own fix. Wez's reset explanation.

For our store, specify full reset, soft reset, screen switching, prompt start, process exit and acknowledgement separately. Test them at their entry points. A passing store test cannot prove that an incoming OSC sequence reaches it.

CONTRIBUTING asks for tests with comments explaining intent and documentation of behavior. It recommends fast cargo check iteration. Its old GUI directory reference has aged; use current source paths. The progress documentation also lags behind the current built-in display. Contribution guidance · A concrete stale claim.
