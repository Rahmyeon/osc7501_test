How much Rust is enough to start?

Comfort with the fundamentals gets you into the parser and record model. Intermediate reading skills help you finish the mux integration. You can build that skill during the project.

This is a practical judgement based on the OSC 9;4 implementation we traced. It is not a formal prerequisite list or a promise about completion time.

The two topics most worth practising early are ownership and enums and pattern matching.

The ownership problem in miniature

A parser may borrow text from an input buffer. A persistent record needs text that remains valid after that buffer is gone. An owned String is a straightforward choice.

Owned text survives the inner scope

let message = {
    let input = String::from("Approval needed");
    input.as_str().to_owned()
};
println!("{message}");

This is valid. The returned String owns a copy of the characters. Dropping input leaves message intact.

This borrow outlives its owner

let message = {
    let input = String::from("Approval needed");
    input.as_str()
};
println!("{message}");

The compiler rejects this. input is dropped at the closing brace, so the borrowed text cannot be used afterwards.

Illustrative Rust snippets, not a protocol parser or a live compiler. Borrowing is valid when the owner lives long enough. Owned text simplifies this particular storage problem; cloning every value is not the general solution.

Learn these when you reach integration

For the pane interface, learn to read traits and implement an existing trait method. For mux changes, learn the existing serialization derives and how messages are delivered. For shared state, understand why the code uses Arc, locks, and async move.

You should understand the locking and ownership assumptions of code you change. The existing architecture gives you patterns to follow; this feature should not require designing a new concurrency system.

The official shared-state concurrency chapter explains the Arc and Mutex pattern. In WezTerm, the local pane alert handler is a concrete example of an existing trait implementation and async move closure.

Advanced macro authoring, unsafe Rust, FFI, and the internals of async runtimes are outside the expected starting requirements. Explicit lifetime annotations may appear while reading, but owned records can keep much of the new model code simple.

A useful readiness exercise

Build a small ordinary Rust crate before editing WezTerm. Use simplified input such as state=working:id=build; it is a learning exercise rather than a complete OSC implementation.

  1. Parse the input into a struct with a state enum and an owned ID.
  2. Return a Result for an unknown state or missing required field.
  3. Store records in a HashMap and replace an existing ID.
  4. Remove build/test when clearing build, while retaining builder/test.
  5. Write tests for each behavior and explain the ownership choices.

If you can finish that with documentation and understand the result, you have enough Rust to start the real parser and model. Needing to look things up is expected.

Where your Lua experience helps

If you already edit Neovim and WezTerm Lua configs, tables, callbacks, and tab formatting will be familiar. That work is likely smaller than the Rust implementation. The terminal still needs to parse and retain reports before Lua can display them.

A tested parser and record model form a useful first milestone. Completing the pane API, mux synchronization, and demo gives you a broader project to discuss on your resume. Build confidence from those working stages.

Self-check

A record must retain text after the input buffer is dropped. Which is the straightforward representation?

Should invalid protocol input normally cause a panic?

Do you need to understand an async runtime's internals before writing parser tests?

Start when you can model data, handle errors, manage owned strings, and test a small crate. Use the later integration work to develop your reading skills.
